# 后端数据库

## Agent Runtime 作用域与恢复事实

单一 Agent Runtime 当前建立服务端作用域、恢复事实、计费模型决策循环、工具审批、画布确定性修改与真实生成任务协调；前端入口和事件流仍未开放。五张表职责如下：

- `agent_threads` 固定个人或团队租户、创建用户、领域项目和画布；租户与权限只能由现有画布权限服务签发，浏览器不能提交或覆盖这些身份事实；
- `agent_runs` 保存一次运行的 actor、客户端幂等请求号、显式状态和最后事件序号；`thread_id + client_request_id` 唯一；
- `agent_run_events` 以 `run_id + sequence` 唯一保存有序事件；序号由数据库原子递增，不依赖进程内计数器；
- `agent_checkpoints` 以同一 run/sequence 保存可恢复状态版本；事件、序号和 checkpoint 在一个事务内提交或回滚；
- `agent_tool_calls` 以 `run_id + tool_call_id + action_version` 唯一冻结工具名、完整参数、风险、权限、审批、幂等键、执行开始时间与真实结果；审批和执行只能消费当前 checkpoint 指向的精确调用版本。

Agent thread/run 的所有读取都必须在 SQL 查询中同时约束 tenant、actor、project、canvas、thread 和 run，不允许查询后再用应用内过滤补权限。事件与 checkpoint JSON 有硬字节上限，超限或非法 JSON 显式失败，不截断；这些表禁止保存供应商 Key、Authorization header 或原始上游错误对象。

服务启动迁移只增量创建表和缺失索引。若同名索引定义错误或历史数据已经违反唯一事实，迁移必须保留原数据并显式失败，禁止自动删除、挑选或覆盖冲突记录。真实 PostgreSQL 门禁只能通过 `scripts/tests/run-payment-integration.sh` 使用随机隔离 schema、临时容器和测试数据库执行，不能连接本地或云端业务数据库。

Runtime 每次推进以 `run.step_number` 作为数据库 CAS 代次；run 快照、连续事件序号和 checkpoint 必须在同一事务提交。首次初始化会同时冻结用户原始请求、步数预算、默认模型记录、模型 Key 与工具 schema 版本，并原子创建首个事件和 checkpoint；不同事实复用同一 run 必须冲突。恢复时 checkpoint 的 state version、step、max steps 与 run 状态必须逐项一致，否则显式失败。

工具状态转换使用独立 `state_version`，不会伪增模型 `step_number`。`canvas.read_state` 与 `canvas.read_selection` 每次执行都重新校验完整 Scope、当前权限和 revision；`canvas.apply_ops` 在批准后先持久化 `tool.started` 与 `started_at`，再以 `runId + toolCallId + actionVersion` 派生唯一 `clientMutationId`，复用 `CanvasChange` 的 revision CAS 与幂等事务。个人画布所有者和团队有效 editor/manager 走同一增量 mutation 协议；画布已提交但 Runtime 结果事务中断时，重试只读取同一 CanvasChange 并补齐工具结果，不重复增加 revision。revision 冲突和参数错误作为结构化工具失败回灌主 Agent，权限撤销或基础设施错误保持显式失败，不伪装成成功。

`generation.submit` 在完整 Scope 和 L2 审批后复用现有 `CreateTask` 商业入口，并以 `runId + toolCallId + actionVersion` 派生稳定 Task 与 Billing 幂等身份；重复协调、进程中断和 PostgreSQL 并发重放只允许形成一个 Task、一个 BillingOrder 和一次积分预留。`generation.wait` 只读取当前用户、当前画布、当前 run operation 的同一任务；queued/running 保持等待，失败和取消显式回灌，只有 succeeded 且结果中存在真实媒体 URL 才写入交付证据。Runtime 最终验收从已持久化的成功工具结果构造 canvas revision 与资产事实，不能用模型文本代替真实交付。

每个模型决策步骤以 `run_id + step_number` 生成确定性 Task ID 和 Billing idempotency key，复用既有 `Task + BillingOrder + CreditLedger + ProviderTaskFact + Worker lease` 商业链路。只有具备版本化筷子账号凭据的文本模型可作为当前运行模型；任务创建时冻结 endpoint 与 credential version。`token_usage` 模型在同一创建事务内冻结 Token 价格、输入上界和商业最大输出量，worker 先提交不可重复发送边界，再把相同最大输出量写入真实请求，响应事实持久化后才核对筷子账单。Task 成功后 Runtime 只读取已持久化的严格 JSON 决策并做通用交付验收；决策结构非法时保存受控的 `model_decision_invalid` 反馈并在同一有界 run 内创建下一模型步骤修正，达到步骤上限才终结，禁止文本提取、默认决策或模型降级。上游请求失败仍显式终结 run；所有已成功发出的 Token 请求继续按原账单核对，禁止误退款或重复调用。模型网关禁止直接发起供应商 HTTP，也禁止以普通请求绕过积分、审计、并发或模型冻结事实。

## 历史资源 OSS 迁移

`storage_migration_jobs` 保存一次由管理员创建的本地资源迁移快照与执行事实：

- 目标渠道、Endpoint、Bucket 与路径前缀在任务创建时固化；执行期间平台 OSS 目标发生变化时任务显式失败；
- `total_items`、`committed_items`、`failed_items`、总字节与已提交字节用于展示可核对进度；
- `preparing`、`queued`、`running`、`succeeded`、`partial_failed`、`failed` 是唯一合法状态；
- 进程异常中断时，启动恢复只把 `running` 任务重新排队，不推测上传已经完成。

`storage_migration_items` 以 `job_id + resource_id` 唯一标识快照内的资源：

- 保存原本地对象键、目标 OSS 对象键、大小、源文件 SHA-256、目标 ETag、尝试次数和最后一次失败原因；
- 上传并通过 HEAD 大小与 ETag 校验后，在同一事务中把 `resources` 切换到 OSS 并把明细标记为 `committed`；
- 事务提交前会锁定并核对资源仍为 `local + ready` 且对象键、大小未变化；并发变更会显式失败；
- 迁移不删除数据卷原文件。任何后续空间回收都必须作为独立、再次确认且可审计的操作实现。

## 模型展示与访问策略

`channel_models` 同时保存系统模型的展示配置与服务端访问策略：

- `icon_file`、`icon_mime_type` 保存后台上传的 PNG、JPG 或 WebP 模型图标引用；文件位于受控数据目录，通过登录态模型图标接口读取，不接受用户提交的任意文件路径。
- `marketing_copy` 保存用户悬浮模型选项时查看的推广文案，`promotion_badge` 保存模型名称旁的短促销角标；两者均为展示信息，不参与供应商协议、积分扣费或活动有效期计算。
- `access_policy` 为非空枚举：`authenticated` 表示全部已登录用户，`member` 表示有效会员专属。

有效会员包括处于有效期内的个人订阅用户，以及有效团队订阅下的有效席位成员；Origin 基础权益不属于有效会员。系统模型目录会下发策略与当前用户的可用状态，但真正授权必须在创建计费订单前再次校验，画布禁用状态不作为安全边界。

模型展示、访问策略、计费配置和对应管理员审计在同一数据库事务中保存，避免后台提示失败但策略已经部分生效。模型图标文件采用内容哈希命名和原子写入，数据库只保存受控文件名与 MIME 类型。

## MiniMax 音色目录与克隆审计

`channel_voices` 保存 MiniMax Speech 系统渠道向用户发布的音色目录：

- `channel_id + voice_key` 是逻辑删除范围内的唯一业务键；
- `kind` 区分供应商系统音色、克隆音色与生成音色；
- `access_policy` 和 `compatible_models_json` 分别控制会员访问与可调用模型范围，任务创建前由服务端再次校验；
- `provider_status` 显式记录 `creating`、`pending_activation`、`active`、`uncertain`、`failed`、`missing` 或 `deleted`，不把网络不确定或供应商下架结果伪装为成功；
- `owner_user_id` 为空表示运营侧发布的公共音色，非空表示用户私有克隆音色；用户目录、试听和正式生成均在服务端校验归属，其他用户不可见、不可收藏、不可调用；
- 克隆源音频成功上传供应商后不在本系统持久化，只保存文件名、字节数、SHA-256 摘要和授权确认时间用于审计；
- `channel_id + owner_user_id + idempotency_key` 对非空克隆幂等键建立唯一约束，既防止重复提交产生多个上游音色，也避免不同用户之间共享幂等命名空间。

`user_voice_favorites` 以 `user_id + channel_voice_id` 保存用户收藏关系。收藏写入前必须确认音色对当前用户可见且处于可用状态；删除音色时在同一事务内清理收藏，禁止产生失去归属的偏好记录。

音色同步按供应商完整目录对账：只更新供应商事实字段，不覆盖管理员配置的会员策略、用户归属和兼容模型；已不在目录中的公共历史 `active` 音色会停用并标记为 `missing`，用户私有克隆音色与尚待首次合成激活的音色不会被公共目录同步误删。克隆调用结果不确定时禁止自动重试，必须先同步音色或在 MiniMax 后台按音色标识核对。删除克隆/生成音色时先确认上游删除成功，再在同一管理员操作中删除本地目录；供应商删除失败时本地目录保持不变。

`channel_voice_previews` 保存系统音色的固定试听结果，避免每次点击都重复产生供应商成本：

- `channel_voice_id + model` 为唯一业务键，同一音色和模型只保留一份当前试听缓存；
- 音频二进制、MIME 类型、内容摘要、供应商 `trace_id` 和生成时间同时保存，读取缓存前校验音色标识与内容摘要；
- 试听首次生成仍执行用户登录、私有音色归属、模型访问策略、音色访问策略与模型兼容性校验，并写入请求日志；
- 缓存有效期为 30 天，过期后由单飞并发控制确保同一音色只触发一次重新生成；
- 删除音色时在同一事务内删除对应试听缓存，不保留失去归属的音频数据。

## 图片模型分辨率计费

图片模型价格由 `channel_models.price_strategy` 明确选择：

- `flat`：使用 `channel_models.unit_price_microcredits`。
- `image_resolution`：必须从 `channel_model_price_tiers` 精确匹配 `1K`、`2K` 或 `4K`。

`channel_model_price_tiers` 以 `channel_model_id + resolution + input_variant` 组成唯一约束，保存档位单价、供应商参考成本区间、参考币种与价格版本。同一模型和分辨率可以保存多个输入规格，但同一输入规格只能有一档；历史两列唯一键硬切到三列唯一键，旧档位明确回填为 `standard`，冲突数据会使迁移失败而不会被删除或挑选。

`billing_orders` 包含 `price_tier_id`、`pricing_resolution` 与 `pricing_input_variant`，并继续保存 `unit_price_microcredits`、`price_version`、数量和最终金额。订单创建后使用这些快照解释历史账单，后台后续调整价格不会重算旧订单。

Agent 文本模型使用同一张 `billing_orders` 的 `token_usage` 模式，不建立平行账本。订单在请求前冻结 Token 价格快照、1.0 倍率、最大输出量、服务地址版本、凭据版本与预留积分；流式请求强制要求上游返回 usage，响应后持久化本地 usage 状态（`reported`、`missing` 或 `invalid`）及输入、缓存命中、输出 Token。Chat Completion 响应 ID 必须符合 `chatcmpl-<task_id>`，计费订单仅保存账单接口可精确查询的内部 `task_id`。筷子账单核对同时保存订单号、任务号、任务状态、账单状态、计费单位 `fen`、账单总 Token 和实扣金额。`pending` 事实由带租约的 worker 继续核对且绝不重发模型请求；`failed` 的零扣费事实与积分退回在同一事务完成；`succeeded` 以筷子实扣金额为资金真源结算并释放差额。首版只允许 1.0 倍率，避免预留公式与实扣换算产生双重口径。

服务启动迁移会把历史空 `price_strategy` 显式更新为 `flat`；新建和编辑模型时必须明确提交价格策略，服务端不会根据模型名称或缺失字段推测策略。

## 平台凭据版本与供应商事实

`provider_accounts` 是供应商接入的持久化根，保存供应商类型、运营名称和启停状态。其下游关系如下：

- `provider_endpoint_versions` 追加保存 Base URL 版本；同一账号只允许一个 `active` 版本，激活以期望旧版本做事务并发校验，旧版本只转为 `retired`，不覆盖 URL；
- `provider_credentials` 以 `provider_account_id + family` 唯一标识一组逻辑凭据，并保存独立的健康状态、最近检查事实和并发上限；
- `provider_credential_versions` 追加保存每次换 Key 的密文、指纹、验证/余额事实和启退时间；同一逻辑凭据只允许一个 `active` 版本；
- `channel_models.provider_credential_id` 将可调用模型显式绑定到逻辑凭据，任务执行时再冻结实际 endpoint 与 credential version，避免换 URL 或换 Key 改写历史任务含义。

筷子账号硬切为一个共享逻辑凭据，全部筷子模型的 `channel_models.provider_credential_id` 指向同一记录；凭据并发上限也以该 ID 为跨渠道共享作用域，不能把视频、图片和 Agent 渠道分别跑满。旧的按系列凭据只用于一次性启动迁移：Key 不一致时迁移显式失败，禁止挑选其中一个或静默覆盖。

任务的供应商事实不再维护平行状态表：`tasks` 保存请求标识、轮询阶段、终态与结果，`billing_orders` 保存渠道、模型、冻结价格档位、供应商请求号和费用核对状态。创建请求在是否已被上游接受无法确认时，账单必须进入 `uncertain`；该任务在管理员完成核对前禁止重新生成，避免重复创建并再次产生供应商费用。取消与上游成功并发时，成功结果和生成记录继续持久化，任务保持取消，账单进入待核对。

金额单位必须随字段解释：用户售价与冻结订单金额使用 `microcredits`；供应商参考成本使用货币 `micros`；供应商原始余额和账单金额使用 `amount_subunits` 十进制字符串。`total_tokens` 和余额同样以十进制字符串保存，避免超过 JavaScript 安全整数或数据库固定整数范围后丢失精度；币种必须由同一事实记录的显式字段解释，禁止跨单位直接相加。

供应商 Key 使用独立的 `enc:provider:v1:` AES-GCM envelope，AAD 同时绑定账号 ID、逻辑凭据 ID 和凭据版本。密文字段与指纹不通过 JSON 返回，也不得写入日志。它与 OSS/支付密文只共享数据目录中的 `.settings-key` 文件所有权和 `0600` 权限规则，不复用无 AAD 的旧加密协议。原始 cipher 无权创建 key；仅 Service 从数据库确认不存在任何非空 `key_cipher` 后，首次写入供应商 Key 才允许以原子独占方式创建 32 字节 key 文件。server 在 worker、readiness 和 listener 启动前查询全部供应商密文，并使用每行真实的账号、逻辑凭据和版本 AAD 逐条解密验证；文件缺失、长度错误、密文篡改、换绑或错误 key 都使启动显式失败，不得创建替代 key 或自动降级。

## 模型商业定价中心

模型商业定价拆分为供应商成本、用户积分售价和经营参数三类数据，后台统一维护，渠道模型页面不再提供分散的价格编辑入口。

`model_pricings` 保存渠道模型的供应商成本口径，包括：

- 单次请求固定成本；
- 视频、音频的每秒成本；
- 文案模型每百万输入、输出、缓存 Token 成本；
- 文案模型用于经营测算的单次预期输入、输出、缓存 Token 数。

`model_pricing_tiers` 保存需要按规格核算的供应商成本档位。图片模型使用 `1K`、`2K`、`4K` 精确匹配，不允许缺失档位时回退到其他分辨率或统一成本。

用户积分售价仍由 `channel_models` 与 `channel_model_price_tiers` 保存，并作为计费订单的价格来源。供应商成本只用于经营测算，不直接替代用户侧计费配置。

`system_settings` 中的 `model_pricing_operations` 保存模型定价中心的经营参数：

- 成本与营收使用的货币；
- 每 1 积分对应的实际营收金额；
- 目标毛利率（基点）。

利润与毛利率仅在供应商成本、积分售价和积分营收换算均已明确配置时计算。任何关键数据缺失时，接口和后台页面必须显示配置不完整，不得使用隐式默认值生成经营结果。

## 团队空间

团队能力由成员关系、订阅快照、团队积分、共享资产、项目权限和开票状态共同组成：

- `teams` 保存团队所有者、名称与启停状态；
- `team_members` 保存成员角色、有效状态和成员月度积分额度，`owner` 角色不可转移、降级或移除；
- `team_invitations` 保存邀请邮箱、角色、有效期和凭证哈希。原始邀请凭证只在创建成功时返回一次，数据库不保存明文；
- `team_audit_events` 追加记录创建团队、重命名、邀请、接受、撤销、角色与积分额度调整、成员移除和主动退出等写操作；
- `team_credit_accounts` 是团队可用积分和预留积分的唯一余额真源；
- `team_credit_ledger_entries` 追加记录团队套餐到账、任务预留、结算消费和退款，并以 `actor_user_id` 归因到实际调用成员；
- `resources.team_id` 将共享文件归属到团队空间，读取必须经过有效团队成员校验；
- `projects.team_id` 表示团队项目归属，`project_collaborators` 保存项目级 `viewer`、`editor`、`manager` 权限覆盖；
- `invoice_requests` 保存会员订单的开票申请、处理结果、发票号码和 HTTPS 文件地址，同一会员订单只能申请一次。

邀请和有效成员共同占用团队会员席位。创建邀请与接受邀请都会在数据库事务内重新校验有效团队订阅和席位数，防止并发接受导致超售。邀请接受还会校验当前登录用户的已验证邮箱与受邀邮箱一致，不能通过邀请编号替他人加入。

`membership_plans` 为团队套餐保存无限任务排队、团队存储字节数、共享资产、项目权限、开票和商业使用授权开关。`membership_orders.plan_snapshot_json` 与 `membership_subscriptions.plan_snapshot_json` 固化购买时权益；后台后续改套餐不会改变已购订阅。迁移只对缺少这些新增字段的旧团队快照按同一套餐补齐商业权益，历史价格、积分、并发和席位保持不变。

`membership_orders` 以非空 `user_id + idempotency_key` 唯一绑定规范化的套餐、团队和席位请求，`request_hash` 只用于服务端核对重复请求，不通过 JSON 返回；历史空幂等键保持为空。支付完整性迁移在复制历史数据后才创建部分唯一索引：同一订单最多一笔 `created`、`pending` 或 `review_required` 可支付交易，同一渠道的非空交易号只能归属一笔交易。已处理回调必须从关联交易取得商户订单号、渠道交易号、金额、币种和到账时间；事实缺失或冲突时迁移显式失败，不会挑选、覆盖或删除冲突记录。

`payment_checkout_sessions` 以 `token_hash` 校验 bearer capability，以绑定订单类型、订单、用户和版本的 `token_cipher` 保存 `enc:v1` 加密 envelope。密文依赖生产 `.settings-key`，只用于订单所有者重放创建请求时恢复同一仍在有效期内的活动 URL；接口、日志与后台列表都不返回哈希或密文。活动会话实际时间已到或状态已过期时，所有者恢复请求会显式冲突，不能把旧 capability 再作为可支付入口返回。历史 hash-only 会话仍可凭原 token 读取，但无法由服务端反向恢复。终态会话保留只读订单事实，创建交易继续只接受活动会话与待支付订单。

`payment_transactions` 的部分唯一索引只覆盖 `created`、`pending`、`review_required`，确保一个订单只有一笔仍可能到账的交易；`provider + provider_trade_no` 的非空唯一约束防止同一真实付款履约多个订单。渠道创建结果不确定时交易保持 `review_required` 并占用付款槽位，只有渠道查询确认未支付或不存在且远端关单成功后才进入 `closed`。后台没有人工标记已支付路径，只能通过强审计的渠道对账进入统一履约或关单。

收银台到期不会释放仍可能到账的交易。若活动会话关联 `created` 或 `pending` 交易，到期事务按订单、checkout、transaction 的统一锁序将交易改为 `review_required` 并把会话改为 `expired`；原二维码不再通过 bearer 接口返回，后台继续以同一商户单执行渠道对账。已有待复核交易或已验签复核事实同样允许会话进入只读过期态，但订单、交易和回调事实不被删除或改写。

`payment_webhook_events` 是验签成功后的独立到账事实。事件先在短事务中按渠道事件 ID、payload digest、商户单、渠道交易号、金额和币种持久化，再由后续履约事务锁定订单及个人用户或团队主体，顺序写入交易、订单、连续不重叠的订阅和积分账本。迟到、第二笔、渠道交易号冲突或履约失败不会删除事实，而是保存为 `review_required` 或 `rejected`；同事件同摘要可幂等重试，不同摘要明确冲突。

`system_settings.site` 的 JSON 聚合统一保存用户协议、隐私政策和会员服务协议。`membershipAgreement` 是独立的可选发布内容；旧配置缺少该字段时按空内容读取，不需要表结构迁移。注册同意门禁只检查用户协议与隐私政策，会员服务协议是否已发布不参与会员订单、checkout、支付交易或履约判定。三份法律内容仍通过同一个管理员写入口完成富文本安全校验和原子保存，审计只记录发布状态，不保存协议正文。

AI 水印规则不写入 `system_settings.site`。`policy_publication_heads` 为每类规则串行分配版本，`policy_publications` 保存不可变的管理规则富文本、水印规范 HTTPS 外链与内容摘要；`user_watermark_preferences` 保存账号当前“去 AI 水印”偏好，`user_policy_consents` 以用户与 publication 唯一键保存已同意版本，`user_watermark_preference_events` 只追加记录每次成功偏好写入。启用去水印时，当前 publication、同意、偏好和事件必须在同一事务内校验并提交；旧 publication 请求直接冲突且不得留下部分事实。`tasks` 冻结模型水印能力、执行指令、实际参数和 publication 版本，后续 worker 重领不得读取账号当前偏好改写历史任务。

`system_settings.membership_storefront` 保存会员商城运营展示配置，包括活动倒计时、界面文案、活动与功能列表、套餐层级生成摘要、生成数量矩阵、会员说明和 FAQ。该配置不能定义价格、积分、并发、席位或团队授权；这些可执行事实只来自 `membership_plans`，并在下单时写入订单快照。

会员订单只在已验签支付事实的统一履约事务中转为已支付。个人订阅按用户主体、团队订阅按团队主体串行计算起止时间；连续购买形成前后衔接且不重叠的订阅。每笔成功支付订单的赠送积分在该履约事务内精确发放一次，生命周期任务不重复补发。模型调用扣费采用预留、结算或任务失败积分退回三段式账本：预留时从可用余额转入预留余额，成功后结算消费，失败时原额退回；这里的账本退回不是微信或支付宝支付退款。团队调用只改变团队积分池并记录实际成员。

团队套餐赠送积分进入 `team_credit_accounts`，不会写入团队所有者的个人账户。团队成员调用模型时，`billing_orders.team_id` 固定账单主体，预留、结算和任务失败积分退回均在同一团队账户事务中完成；成员自然月已用金额由团队账单事实汇总，超过 `team_members.monthly_credit_limit_microcredits` 时调用在扣款前明确失败。额度为 0 表示不设置成员级上限，但仍受团队余额和渠道安全并发限制。

“无限任务”只取消套餐层面的排队数量拒绝，不取消全局 Worker 与渠道安全并发限制。团队存储额度由套餐字节字段配置，不在前端写死；上传会同时校验单文件、用户日上传和团队总存储额度。

团队角色默认映射为项目权限：所有者、管理员为 `manager`，普通成员为 `editor`；项目覆盖可降为 `viewer`。团队项目写入要求有效团队订阅，读取保留给有效成员以保证订阅到期后的数据可访问。项目移出团队或删除时会事务性清理项目权限覆盖，避免旧团队权限泄漏到新归属。

`invoice_requests` 只表示可审计的开票业务状态，不伪造税务结果。标记 `issued` 时必须由后台填写真实发票号码和 HTTPS 文件地址；重复处理使用条件更新拒绝。真实电子发票仍需由税务系统或后续接入的开票服务商生成。
