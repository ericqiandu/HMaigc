# 后台邀请奖励页面排版设计

## 目标

把“邀请奖励”接入已经落地的后台数据页排版体系，在不改变活动开关、套餐奖励、邀请关系、资格取消和分页契约的前提下，统一运营概览、规则配置与关系表格的阅读顺序。

## 页面结构

页面保留 `AdminPageFrame` 作为唯一页框架，内容按以下顺序排列：

1. **运营概览**：连续展示邀请注册关系、已触发首购和累计发放积分三个真实服务端指标。
2. **活动配置**：展示活动总开关及其生效边界，不把开关拆成独立装饰卡片。
3. **套餐奖励**：逐套餐展示好友奖励、邀请人奖励、启停状态和真实同步状态。
4. **邀请关系**：标题栏展示关系总数，表格承载绑定、首购、奖励和资格操作。

页面不新增营销图表。当前接口只提供聚合计数和分页关系，没有可靠时间序列，伪造趋势会造成运营误判。

## 组件接入

- 使用 `AdminDataLayout` 统一纵向节奏。
- 使用 `AdminMetricBand` 与 `AdminMetric` 承载现有三个概览指标。
- 使用 `AdminContentSection` 分别承载活动配置、套餐奖励和邀请关系。
- 活动配置和奖励规则继续复用现有交互与状态，不创建平行业务组件或复制请求逻辑。
- 邀请关系表格继续复用 `AdminTableEmpty`、既有分页和取消资格弹窗。

## 保持不变的业务契约

- 活动总开关仍由现有接口即时保存，提交期间保持锁定。
- 套餐奖励继续逐行比较真实草稿与服务端基线；无修改时不得重复保存。
- 积分仍以微积分为存储单位，页面只沿用现有展示和输入换算。
- 邀请绑定关系不可删除或改绑；取消资格仅在首购发奖前允许。
- 取消资格继续要求明确原因，并展示目标用户和邀请码。
- 翻页继续读取服务端分页事实，不在前端拼接或伪造记录。

## 响应式与可访问性

- 1440px 桌面宽度下保持 1240px 有效内容区，三个概览指标连续横排。
- 1024px 级视口收敛为单列内容节奏，奖励行允许重新排布，不横向挤压输入控件。
- 390px 手机宽度下指标纵向分隔，活动开关、规则字段和保存动作保持不低于 44px 的触控热区。
- 页面只保留一个 `h1`；三个内容分区使用连续 `h2`；表格横向滚动只发生在表格内容区。

## 状态与错误处理

- 首次加载显示共享内容骨架，不展示零值指标或空规则。
- 首次读取失败使用共享错误状态替换整个内容区，并提供原地重试。
- 刷新失败时保留上一次成功数据，同时显示真实失败原因。
- 没有邀请关系时显示真实空状态，不隐藏活动配置和套餐规则。
- 不新增静默回退、默认数据、兼容分支或前端伪成功状态。

## 文件与复杂度预算

生产职责不超过三项：

1. 邀请奖励页接入共享数据布局。
2. 奖励规则和邀请关系标题操作位整理。
3. 页面响应式样式清理。

预计修改不超过 4 个生产文件，净新增生产代码不超过 200 行；超过 50% 必须停止并重新评估。不改后端、数据库、DTO、积分计算、会员套餐或权限。

## 验证

- 定向测试覆盖区块顺序、三个真实指标、规则同步状态、关系总数、加载/错误/空状态和资格取消入口。
- 全量 `bun test`、`bun run build` 通过。
- 重建本地 Docker 镜像，确认后端和 Web 健康且继续绑定主仓 `.local/data`。
- 使用真实浏览器验证 1440×900、1024×768、390×844，无页面级横向溢出，规则操作和表格滚动保持局部。
