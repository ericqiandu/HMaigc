# Agent Token 计费设计

## 目标

将 Agent 文本模型从“每次请求固定积分”硬切为“按上游真实 Token usage 结算”。首版仅覆盖当前实际使用的筷子 DeepSeek V4 Flash 与 V4 Pro，按供应商成本价和 `1.0` 倍率收取用户积分。

系统继续遵循 `1 元 = 100 积分`。历史固定按次账单保持原样，不追溯重算。

## 首版范围

- 筷子 DeepSeek V4 Flash：缓存命中输入 `0.02 元/百万 Token`、未命中输入 `1 元/百万 Token`、输出 `2 元/百万 Token`。
- 筷子 DeepSeek V4 Pro：缓存命中输入 `0.025 元/百万 Token`、未命中输入 `3 元/百万 Token`、输出 `6 元/百万 Token`。
- 每一次真实模型请求独立计量；同一用户操作中的主 Agent、自修复和子 Agent 调用在展示层汇总。
- 工具调用本身不收费。工具内部触发的文本、图片或视频模型按各自模型账单独立计费。
- 请求前预冻结；请求后优先使用筷子账单接口返回的真实扣费金额结算，多冻结部分自动退回。

首版明确不做：官方 DeepSeek 分时价格、通用供应商计费规则引擎、套餐档位、历史账单迁移、图片和视频价格重构。

## 简化原则

复用现有 `BillingOrder`、积分账户、积分流水和 `ApiCallLog`，不建立平行账本。生产代码只新增一种 `token_usage` 计费模式和一个统一的 Token 结算入口。

价格是渠道模型配置的一部分，并保存价格版本。任务创建后冻结价格快照，后台后续改价不得影响已开始的请求。

## 计量事实

每笔 Token 账单至少冻结并保存以下事实：

- 渠道、模型、价格版本和倍率；
- 缓存命中输入单价、未命中输入单价、输出单价；
- 预估输入 Token、允许的最大输出 Token 和预冻结积分；
- 上游请求 ID；
- 实际输入 Token、缓存命中 Token、实际输出 Token；
- 筷子扣费订单号、扣费状态、账单总 Token 和账单金额（分）；
- 最终积分、账单状态和异常原因。

`cachedTokens` 必须是 `inputTokens` 的子集。未缓存输入量按 `inputTokens - cachedTokens` 计算。任何负数、溢出、缓存量大于输入量或缺失必要字段都属于计量异常。

## 预估金额计算

全部金额使用整数运算，最终向上取整到最小微积分，禁止浮点结算。

```text
未缓存输入 = 输入 Token - 缓存命中 Token

预估微积分 = ceil(
  (未缓存输入 × 未缓存输入单价微元/百万Token
   + 缓存命中 × 缓存输入单价微元/百万Token
   + 输出Token × 输出单价微元/百万Token)
  × 100积分/元
  × 倍率基点/10000
  ÷ 1,000,000
)
```

其中一积分等于 `1,000,000` 微积分。价格与倍率必须作为账单快照持久化。该公式用于请求前预冻结与成本对账，不替代筷子已成功扣费订单返回的真实金额。

筷子渠道的已确认换算契约为 `1 点 = 1 元 = 100 分`。结合本系统 `1 元 = 100 积分`，筷子成功账单 `amount` 的每 `1 分` 正好对应本系统 `1 积分`。首版倍率为 `1.0`，因此最终用户积分等于筷子成功账单的整数 `amount`。系统必须同时保存原始 `amount`、单位和价格版本，禁止通过浮点数二次换算。

## 请求与结算流程

1. 系统使用与渠道模型匹配的 tokenizer 根据实际请求内容计算输入 Token；模型无法提供匹配 tokenizer 时不得发布为 Token 计费模型。
2. 系统使用该模型允许的最大输出 Token 计算最大费用，并在同一事务内检查余额、建立账单和冻结积分。
3. 预冻结成功后才允许调用上游。
4. 上游返回后保存可用的输入、缓存命中和输出 Token，以及可关联筷子账单的 `task_id`。
5. 系统调用 `POST /ai-open-platform-api/v1/user/billing/list`，按 `task_id` 精确查询扣费记录。`status=pending` 时有界轮询；`status=succeeded` 时使用账单 `amount` 作为真实供应商成本；`status=failed` 时退款。
6. 系统按冻结倍率计算最终积分，并在同一事务内完成结算和退回差额。首版倍率为 `1.0`，所以最终积分等于筷子账单 `amount`。
7. `ApiCallLog` 保存响应 usage；本地账单保存筷子 `order_id`、`task_id`、`total_tokens`、`amount` 与状态，运营页面可以交叉核对。

为避免按模型理论最大输出冻结过多积分，Agent 渠道必须配置并实际下发一个商业允许的 `maxOutputTokens`。预冻结和上游请求使用同一个值，禁止仅在计费端使用较小上限。

## usage 缺失与失败

- 上游明确拒绝且筷子账单确认未扣费：全额退款。
- 上游响应缺少 usage，但返回了可查询账单的 `task_id`：仍按 `task_id` 自动查询筷子账单并结算，不需要人工核算 Token 分类。
- 筷子账单为 `pending`：保持冻结并有界轮询，禁止重复调用模型。
- 筷子账单为 `succeeded`：以 `amount` 为最终成本；本地推算金额只用于差异告警，不得覆盖上游真实账单。
- 筷子账单为 `failed`：退款并记录上游订单事实。
- 上游未返回可关联账单的 `task_id`、查询接口持续失败或在核对期限内没有唯一账单：进入 `metering_uncertain`，展示明确原因并进入管理员核对。
- 上游返回的 usage 非法但筷子账单可唯一关联且已成功：仍按真实账单 `amount` 结算，并记录 usage 数据质量告警；账单也无法可靠关联时才进入 `metering_uncertain`。
- 重试、回调和状态轮询必须幂等；同一模型请求只能冻结一次、结算一次。

匹配渠道模型的 tokenizer 只用于请求前预估，不能替代最终 usage，因为本地不知道供应商缓存命中、隐藏推理 Token、供应商注入内容和内部工具调用事实。

## 用户体验

- 发送前显示“预计最多冻结 X 积分”，不是伪装成最终费用。
- 完成后显示“实际消耗 X 积分”，并展示退回的冻结差额；该数字来源于筷子成功扣费订单。
- 一次 Agent 操作可以展示总消耗，并可展开查看每个模型请求的模型、Token 和积分明细。
- 计量异常时显示“积分仍处于冻结核对中”，不得显示已扣费或伪成功。

## 一致性与并发

- 建账、冻结账户和预留流水属于一个事务。
- 结算、退回差额、更新账单和消费流水属于一个事务。
- 账单使用幂等键和状态条件更新，重复响应不得重复扣费。
- 余额不足必须在调用上游前失败。
- 同一用户的并发请求必须锁定账户事实，禁止透支。

## 验收标准

- Flash 与 Pro 的缓存输入、未缓存输入和输出 Token 均能精确计算。
- 预冻结大于实际费用时自动退回差额。
- 余额不足和并发请求不能产生负余额。
- usage 缺失但存在 `task_id` 时会按筷子账单自动核对；无法唯一关联账单时进入 `metering_uncertain`，不会默认扣一积分。
- 筷子账单成功、失败和处理中三种状态分别结算、退款和保持冻结。
- 筷子账单金额与本地Token价格推算不一致时保留真实金额并产生运营告警。
- 重复回调只产生一份结算流水。
- 主 Agent、自修复与子 Agent 的真实模型请求分别计量，并在用户操作层汇总。
- 历史固定按次账单不受影响。
- API 日志、账单和积分流水中的 Token 与金额事实一致。

## 实施预算

- 生产职责：Token 价格契约、预冻结/结算、用户费用展示，共三项。
- 生产文件：预计不超过八个。
- 生产净新增：预计不超过约八百行。
- 昂贵门禁：稳定后执行后端全量测试、竞态测试、构建，并对 Agent 请求做一次本地端到端核对。
- 若实现需要新增独立计费状态机、跨越图片/视频账单重构或超过预算 50%，停止实施并重新拆分，不继续堆补丁。
