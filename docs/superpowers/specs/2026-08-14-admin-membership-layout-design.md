# 会员管理页面统一排版设计

## 业务目标

把会员管理页纳入当前后台统一的数据页语言，使运营人员能按固定顺序理解会员业务：先看运营事实，再选择业务模块，最后处理当前模块的数据或配置。改造只调整信息架构、视觉层级与响应式表现，不改变套餐、商城、订单、发票、支付交易或回调审计的业务契约。

## 当前事实

- 页面包含六个真实模块：套餐与权益、商城展示、会员订单、开票处理、支付交易、回调审计。
- 各模块按需读取自己的服务端数据；未进入的模块不得伪造统计值或提前请求。
- 套餐编辑、订单关闭、开票处理和渠道对账已有独立提交状态、失败反馈与未保存保护。
- 当前页面已经具备概要、模块导航和内容区，但概要、标签栏与表格分别使用私有表面，层级和其他统一后台数据页不一致。

## 方案

采用单一路径的共享数据布局：

1. **会员运营概览**：复用后台共享指标表面，展示套餐目录、待核款订单和当前运营提示。未读取订单时明确显示“进入订单后读取”，不展示零值假事实。
2. **模块导航**：桌面端保留六项紧凑标签导航；移动端保留单一下拉选择器。导航只负责切换模块，不复制统计和操作。
3. **当前模块内容**：所有模块进入同一个共享内容表面。套餐表、商城表单、订单表、开票面板、支付交易表和回调表继续由现有业务组件负责。

页面顺序固定为“概览 → 模块导航 → 当前模块内容”。标题区只保留当前模块适用的刷新操作。

## 视觉规则

- 使用 `AdminDataLayout`、`AdminMetricBand`、`AdminContentSection` 等现有共享组件，不创建会员页私有卡片体系。
- 每个独立区块最多一层可见圆角边界；表格、表单和标签导航不得继续圆角套圆角。
- 通过留白、背景明度和弱分隔表达层级，不增加渐变、重阴影或装饰图标容器。
- 桌面端概览保持紧凑横向布局；窄屏收为单列。
- 390–1279px 的模块选择与主要操作保持至少 44px 热区，页面级横向滚动为零；宽表只允许在表格内部滚动。

## 状态与交互

- 首次加载失败继续使用 `AdminContentError`，不得渲染空表或伪造指标。
- 刷新失败继续保留最近一次成功数据，并显示可重试的真实错误。
- 切换模块继续按需加载，不引入预加载或隐式回退。
- 套餐编辑脏状态、浏览器离开保护、订单关闭、开票处理和支付渠道对账逻辑保持不变。
- 不修改 API、DTO、后端、数据库、计费、支付或权限。

## 可访问性

- 页面只保留一个 `h1`，概览和当前内容使用连续的 `h2` 层级。
- 桌面标签保持可键盘切换；移动端下拉具有明确可访问名称。
- 纯图标操作必须保留 `aria-label`；加载、错误和空状态继续向辅助技术暴露真实语义。

## 实施边界与预算

- 生产职责：顶层信息架构、共享表面映射、响应式样式，共 3 项。
- 预计生产文件不超过 5 个，净新增生产代码不超过约 350 行。
- 不拆分六个模块为独立路由，不重写子模块业务组件，不调整后台导航顺序。
- 若实现需要修改后端契约、支付状态机或超过预算 50%，停止实施并重新设计。

## 验收

- 真实页面顺序为概览、模块导航、当前模块内容。
- 六个模块均可切换并保留原有功能、加载、错误和空状态。
- 桌面、平板和 390px 移动视口无页面级横向溢出。
- 受影响测试、全量 Web 测试、生产构建和包体预算通过。
- 本地仅重建无状态 Web 容器；后端容器和主项目 `.local/data` 保持不变。
