# 会员付款界面统一设计

## 背景

当前会员购买链路分为两个视觉与信息结构不同的界面：会员页先用 `MembershipPurchaseModal` 确认套餐、团队和席位，创建订单后再跳转到 `/pay/:token` 的独立收银台。前一个弹窗只展示金额与积分摘要，后一个收银台只展示订单号、应付金额、支付渠道和二维码，用户无法在付款前再次核对已购买的套餐快照。

用户要求参考 LibTV 的创作会员与团队会员付款界面，统一为“左侧订单事实、右侧扫码支付”的深色收银台，同时保留 HMaigc 现有真实套餐、团队、席位、订单与支付渠道能力。

## 已确认事实

- 参考站真实桌面创作付款弹窗约为 `782×472px`，左侧订单区约 `462px`，右侧扫码区固定约 `320px`。
- 参考站真实桌面团队付款弹窗约为 `881×604px`，左侧订单区约 `561px`，右侧扫码区同样约 `320px`。
- 两种弹窗共用 16px 外层圆角、深灰双表面、青色选中态、紧凑订单明细和大号应付金额；团队版本额外展示周期、席位与团队总积分。
- 参考站在 `390×844px` 下仍保留桌面双栏，导致扫码区横向溢出。该行为不作为 HMaigc 的响应式参考。
- HMaigc 的会员订单已经保存不可变 `planSnapshotJson`、席位、单价、总价和币种，无需新增数据库列即可构造可信结算摘要。
- 当前 `PaymentCheckout` 只返回订单号、金额、状态、有效期和可用渠道，无法可靠渲染会员套餐、周期、席位、积分、原价与优惠。
- HMaigc 同时支持支付宝和微信支付，不能把参考站的“固定支付宝”写死为唯一渠道。

## 目标

- 创作会员与团队会员使用同一套付款页面骨架和视觉语言。
- 付款前展示由服务端订单快照派生的完整订单事实，不从当前套餐配置重新读取或在前端拼造历史价格。
- 保留现有“确认配置后创建不可变订单，再进入收银台”的安全顺序。
- 保留真实支付渠道选择、二维码创建、轮询、过期、成功和失败语义。
- 移动端改为上下布局，不复制参考站的横向溢出。
- 不改变会员套餐权益含义，但在不改变已支付历史事实的前提下补齐下单、收银台和支付交易的幂等、并发、审计与异常到账边界。

## 非目标

- 不把点击套餐卡直接等同于创建订单或支付交易。
- 不允许用户在已经生成二维码后修改套餐、周期、团队或席位。
- 不新增自动续费协议、花呗分期、优惠券、固定支付宝或参考站品牌文案。
- 不新增支付渠道或支付网关，不实现当前渠道并不存在的自动续费、分期或退款承诺。
- 不重做会员套餐展示页、积分超市或后台套餐编辑器。

## 方案选择

采用“保留两阶段业务流程，统一订单确认与真实收银台视觉，并由收银台接口返回不可变会员摘要”的方案。审查同时确认现有支付链路存在并发生成多个真实付款码、重复创建收银台使先返回链接失效以及 bearer token 被访问日志记录的问题；这些问题与新收银台直接共享同一真实资金链路，必须在同一交付中修复，不能只做视觉换皮后宣称可用于生产收款。

没有选择纯 CSS 改造，因为当前收银台接口缺少套餐快照事实，纯前端无法在刷新、历史待支付订单和直接链接场景中可靠恢复订单明细。也没有选择“点击套餐后直接生成二维码”的单弹窗方案，因为它会在用户尚未确认团队和席位时制造废弃订单或支付交易，并引入取消、重建和并发修改问题。

## 业务流程

1. 用户在会员页选择创作或团队套餐。
2. `MembershipPurchaseModal` 使用统一的左侧订单视觉确认可编辑事实：套餐、周期、团队和席位。此时不创建订单或支付交易。
3. 用户明确点击“创建订单并支付”后，前端为规范化的 `{planId, teamId, seats}` 请求指纹分配一次性的 `Idempotency-Key` 创建不可变会员订单；同一指纹的网络重试复用该键，任一购买输入变化必须生成新键。随后幂等创建或重放该订单唯一的活动收银台会话并跳转到 `/pay/:token`。
4. 收银台读取服务端返回的会员订单摘要。摘要必须来自该订单的 `planSnapshotJson` 与订单金额字段，而不是当前套餐表。
5. 用户选择真实可用支付渠道并显式生成付款码；同一订单任一时刻只允许存在一笔可支付交易。重复请求和刷新必须返回同一商户订单与二维码，生成二维码后锁定渠道。收银台到期时 `created/pending` 交易原子转入 `review_required`，不再返回旧二维码，但继续占用同一付款槽直到渠道对账确认终态。
6. 页面轮询订单状态；支付成功、过期、关闭或失败均使用明确状态替换可支付界面。`refunded` 仅是当前模型枚举，在真实退款通道上线前必须显示“状态待核对”而不是声称款项已经退回。

## 后端结算契约

### 返回模型

`PaymentCheckoutView` 增加可辨别的订单摘要：

- `orderType` 继续区分 `membership` 与 `credit_topup`。
- `orderStatus` 与 `checkoutStatus` 分离，禁止继续用会员订单状态类型承载积分订单或收银台状态。
- 返回服务端 `serverNow`、`expiresAt` 与可选 `activeTransaction`；后者只包含恢复页面所需的 `provider`、`status`、`codeUrl` 与 `expiresAt`，不得包含渠道密钥或内部失败载荷。
- 公共交易创建接口改为专用最小响应 DTO，字段与 `activeTransaction` 一致；禁止继续直接序列化含 `userId`、内部 `orderId`、商户审计字段和失败详情的数据库模型。
- 会员订单返回 `membershipSummary`；积分充值订单返回独立的 `creditTopupSummary`，不得伪造会员字段。两个摘要按 `orderType` 构成互斥联合。
- `membershipSummary` 使用已经落地的最小不可变投影：
  - `audience`：`personal | team`
  - `code`
  - `name`
  - `tier`：冻结套餐的展示层级字符串，不在收银台引入第二套枚举
  - `billingCycle`：`month | year`
  - `seats`
  - `actualPriceCents`：整笔订单实付总额
  - `originalPriceCents`：整笔订单原价总额
  - `creditsPerPeriod`：单席位周期积分，单位为 microcredits
  - `totalCreditsPerPeriod`：整笔订单周期总积分，单位为 microcredits
- 币种由 `PaymentCheckoutView.currency` 统一提供，两个互斥摘要不重复保存。当前能力是一次性支付且不自动续费，这是支付能力规则，不伪装为订单快照字段。
- `1 积分 = 1,000,000 microcredits`；接口保持整数 microcredits，只有前端展示层执行换算和本地化格式化。

### 数据来源与校验

- 套餐名称、等级、受众、周期、原价、积分和币种只从订单的 `planSnapshotJson` 解析。
- 席位、单价、总价与团队 ID 以订单记录为准，并与快照价格、币种和受众进行一致性校验。
- 收银台接口使用随机令牌作为 bearer capability。团队名称不在不可变订单快照中，因此本次不向该接口追加可变团队资料，也不因展示需要扩大令牌可读范围；团队名称只保留在创建订单前、已经登录且经过团队权限校验的确认弹窗中。
- `totalCreditsPerPeriod = creditsPerPeriod × seats`，个人订单席位必须为 1；价格与积分乘法必须先做整数溢出检查。
- 服务端验证 `actualPriceCents = snapshot.priceCents × seats = order.totalPriceCents`，`originalPriceCents = snapshot.originalPriceCents × seats`。因此前端只在需要展示单席位事实时做可整除派生，不读取当前套餐。后台允许原价为 `0` 或不高于实付价；这种快照仍是合法订单事实，但不构成优惠。只有 `originalPriceCents > actualPriceCents` 时才由展示模型派生正数优惠并显示划线原价。
- 快照缺失、损坏、套餐 ID/币种/价格不一致时明确返回错误，禁止退回当前套餐或默认值。
- `month | year` 付费周期必须具有严格大于零的价格；后台保存、启动完整性扫描和下单都拒绝 `priceCents <= 0`。本轮不实现零元扫码或隐式免费开通；真正的免费套餐继续使用独立 `free` 周期。
- `GET checkout` 对合法 bearer 即使已经 `expired` 或 `consumed` 也返回只读事实视图；创建支付交易的写接口继续严格拒绝非活动、非待支付状态。

## 支付一致性与持久化

### 必要迁移

以下迁移是为封闭已确认的真实资金竞态，而不是为了视觉样式增加冗余数据：

- 会员订单增加非空默认空字符串的 `idempotencyKey` 与 `requestHash`，按用户与非空幂等键建立唯一约束，行为与现有积分充值订单一致。相同键和相同请求重放原订单；相同键绑定不同请求必须冲突；历史空值只做受控的 `NULL -> ''` 规范化，不伪造幂等键。
- 收银台会话增加非空默认空字符串的加密 token envelope。数据库继续以 SHA-256 哈希查询 bearer；密文只用于订单所有者重试创建时恢复同一活动 URL，禁止返回到管理接口或日志。历史 hash-only bearer 仍可读取，但不能反向恢复或静默轮换。
- 支付交易在 `(order_type, order_id)` 上增加仅覆盖 `created | pending | review_required` 状态的部分唯一索引，用数据库唯一约束保证同一订单只能有一笔仍可能到账的交易；进入确定的 `failed | closed` 后才由索引谓词释放槽位，不新增需要应用代码维护且可能与状态漂移的 `payableKey` 字段。
- 支付交易对非空 `(provider, provider_trade_no)` 建立唯一约束，避免同一真实渠道付款被不同回调或不同商户单重复履约。
- 迁移分为基础表/字段与数据复制后的完整性约束两阶段；错误同名索引、谓词漂移、历史 payable 冲突、渠道交易号冲突或现存零价付费周期套餐必须显式失败。除已授权的历史 `NULL -> ''` 规范化与可证明回填外，不改写订单金额、快照、已支付状态或权益事实。

### 并发与异常到账

- 订单、活动收银台与 payable transaction 的 claim 必须在 PostgreSQL 事务中锁定并重新校验订单仍待支付、收银台仍活动、且不存在 paid 或验签成功后待复核的到账事实；数据库唯一约束是最终裁决，进程内锁或按钮禁用不能作为一致性依据。回调履约使用同一订单锁顺序，避免付清释放索引槽位后并发再建第二笔交易。
- 会员履约除订单锁外还必须锁定权益主体：个人会员锁用户行、团队会员锁团队行。在同一事务和同一主体锁内重新读取最新订阅截止时间、计算新订阅起止、插入订阅并发放积分；不同订单对同一主体并发到账时，订阅必须连续且不重叠，不能在事务外预计算期限。
- 渠道下单以已经持久化的唯一商户订单号执行。请求超时或响应丢失时不能盲目新建第二笔交易，交易进入仍占用槽位的 `review_required`。管理员可通过强审计的渠道查询/关闭动作重新核实该商户单：确认支付则进入统一履约，确认未支付且渠道关闭成功才置 `closed`，仍不确定则保持复核态。
- 验签回调继续核对商户、金额、币种、渠道交易号与 payload digest。重复事件同 digest 幂等；同 event ID 不同 digest 明确冲突并告警。
- 已取消、已过期、第二笔到账或履约事务失败时，验签成功的到账事实必须在独立事务持久化为 `review_required/rejected` 并产生结构化告警，不能因业务事务回滚而丢失。未实现真实退款调用前，界面和接口不得声称“已退款”。
- 渠道 ACK 语义必须确定：验签失败或到账事实本身未能提交时返回失败以请求重试；事实已持久化且属于永久业务拒绝、迟到/重复付款或需人工复核时返回成功以停止无意义重试；事实已持久化但履约发生可重试数据库故障时保留 `review_required`、返回失败，并允许同 event ID/同 digest 的后续通知重新尝试统一履约。event ID 同值但 digest 冲突不得覆盖原事实，并返回失败告警。
- 自动履约使用明确的 system actor；订单、订阅、积分账本、交易、收银台和成功回调事件保持同事务 exactly-once。

## 前端组件边界

### 共享展示模型

新增纯函数把 `membershipSummary` 转换为页面展示模型，负责金额、积分、周期和折扣文本；组件不得自行解析 `planSnapshotJson`。

### 订单确认弹窗

- 继续由 `MembershipPurchaseModal` 负责创建订单前的可编辑输入。
- 创作会员展示单一商品卡与订单预览。
- 团队会员展示套餐、团队选择/新团队名称、席位步进器、单席位与团队合计。
- 弹窗不展示二维码，也不声称订单已经创建。
- 提交按钮仍为“创建订单并支付”，提交期间锁定关闭与重复提交。

### 真实收银台

- `PaymentCheckoutPage` 采用统一 `MembershipCheckoutShell`：左侧订单面板，右侧支付面板。
- 创作订单左侧展示套餐卡、积分数量、周期、原价、优惠与应付金额。
- 团队订单额外展示席位数量、单席位积分与团队总积分；不通过 bearer 收银台令牌暴露团队名称。
- 右侧只渲染接口返回的可用渠道。多渠道时保留明确选择；没有可用渠道时显示真实错误。
- 生成二维码前显示支付渠道与“生成付款码”操作；生成后显示对应渠道名称、二维码、订单倒计时和“请勿重复支付”。
- 当前渠道均为一次性扫码支付。周期只能写“按月购买”或“按年购买”，并明确“到期不自动续费”；禁止照抄“连续包月、次月续费、随时取消”。订阅起点可能按现有订阅顺延，付款前不得展示尚未形成事实的精确到期日。
- 页面刷新、历史待支付订单和直接打开链接时完全依赖服务端结算摘要恢复，不依赖路由 state 或本地缓存。
- `credit_topup` 继续使用现有通用摘要，不能因为会员专属字段缺失而失败。

## 视觉契约

- 桌面收银台最大宽度约 `880px`；创作订单可按内容收窄，但右侧支付面板保持约 `320px`。
- 外层只有一层 16px 圆角与弱边界，符合单层圆角边框原则。
- 左侧使用较深表面，右侧使用一级更亮表面；订单明细使用单层连续次级表面与弱分隔，不创建多层圆角卡片。
- 左侧标题 18–20px / 600，分区标题 13–14px / 600，正文 13–14px；应付金额使用青色强调，不复制参考站品牌蓝。
- 套餐选中态使用 HMaigc 现有会员青色语义；原价使用删除线，优惠和积分只展示真实数据。
- 关闭按钮、渠道按钮、席位步进器和移动端操作热区不低于 44px；所有图标操作提供可访问名称和 2px 可见焦点。
- 背景使用收银台页面自己的暗色遮罩与轻量模糊，不把会员页 DOM 复制到支付路由作为假背景。

## 响应式

- `> 760px`：左右双栏，右侧固定约 `320px`，左侧吸收剩余宽度。
- `<= 760px`：改为单列，订单在上、支付在下；宽度为视口减 24px，禁止横向滚动。
- 移动端二维码尺寸按可用宽度收缩，但不得小于可可靠扫码的产品下限；若空间不足则允许页面纵向滚动。
- 团队周期卡和订单明细在窄屏换行，不使用横向裁切掩盖内容。
- 验收覆盖 `1440×900`、`768×1024` 与 `390×844`，并核对 `scrollWidth === clientWidth`。

## 状态与失败

- 首次加载：保留固定骨架，不闪现空金额或默认套餐。
- 接口失败：展示真实原因和原地重试，不渲染伪造订单摘要。
- 快照无效：后端显式失败，前端展示“订单信息无法验证”，禁止继续生成付款码。
- 渠道下单失败：保留订单摘要和已选渠道，展示真实错误，可由用户重试。
- 订单过期或不可支付：禁用支付操作并提供返回会员中心关闭旧订单后重新下单的入口；活动时间已到或已过期的 checkout 不得由所有者创建接口恢复为可支付链接，存在付款事实时必须等待渠道对账。
- 已支付：替换为成功状态，继续轮询时不得重复创建交易或发放权益。
- 轮询响应必须按服务端事实和时间顺序收敛；较晚到达的旧响应或瞬时网络失败不得覆盖已经确认的 paid 状态，也不得清空已加载的订单摘要与二维码。
- 组件卸载、切换渠道和重复点击不得泄漏计时器或并发创建多个交易。

## 安全与缓存

- `/pay/:token`、`GET /api/payments/checkout/:token` 与交易创建响应均使用 `Cache-Control: private, no-store`；兼容旧代理时同时发送 `Pragma: no-cache`。
- Web Nginx 与 Gin 请求日志必须对 `/pay/<token>` 和 `/api/payments/checkout/<token>` 使用固定占位路径，禁止记录 token、查询参数、token hash 或 `codeUrl`。
- 继续使用 `Referrer-Policy: no-referrer`。生产 `checkoutBaseURL` 与支付 `notifyURL` 必须为 HTTPS；localhost/环回 HTTP 只允许显式开发环境，禁止生产静默放宽。
- bearer 响应遵循最小披露：不得新增 `userId`、`teamId`、`teamName`、原始 `planSnapshotJson` 或内部渠道错误。

## 回滚边界

变更包含结算 DTO、会员/收银台 UI、日志与缓存策略，以及上述最小幂等字段和唯一约束迁移；不修改历史订单金额、套餐快照、已支付权益或积分事实。迁移、后端状态机与前端消费必须作为同一版本交付，并在迁移前备份、迁移失败非零退出、应用切换失败可回滚到上一完整版本。由于数据库结构变更属于高风险操作，进入实现前必须获得用户对该明确迁移范围的单独授权。
