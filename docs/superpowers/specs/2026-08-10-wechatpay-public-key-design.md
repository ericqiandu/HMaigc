# 微信支付公钥单一路径设计

## 目标

HMaigc 的微信 Native 扫码支付硬切到微信支付 API v3 当前推荐的“微信支付公钥”模式。后台必须完整保存并使用商户身份、公钥 ID、公钥和 API v3 密钥；请求、应答与回调必须绑定同一个公钥 ID，任何缺失、不一致或验签失败都原地失败并留下可检索的安全日志。

本次不保留微信支付平台证书模式，不增加平台证书与公钥双轨选择。支付宝继续使用原有平台公钥契约，不受本次变更影响。

## 业务边界

- 支持直连商户的微信支付 API v3 Native 扫码下单、查单、关单与支付成功回调。
- 商户必须已开通 Native 支付、绑定已认证 AppID，并在微信商户平台申请商户 API 证书、微信支付公钥及公钥 ID、API v3 密钥。
- HMaigc 只保存服务端支付凭据；私钥、API v3 密钥、公钥内容不回显、不进入普通请求日志或审计详情。
- 不实现微信 OAuth、JSAPI、小程序内支付、APP 支付、H5 支付、退款或自动续费。

## 配置契约

### 微信渠道

微信渠道配置硬切为以下字段：

- `enabled`：渠道是否启用。
- `appId`：已与当前商户号绑定的 AppID。
- `merchantId`：微信支付商户号。
- `merchantSerialNo`：与商户私钥对应的商户 API 证书序列号。
- `merchantPrivateKey`：`apiclient_key.pem` 的完整 PEM 内容。
- `wechatpayPublicKeyId`：微信商户平台显示的 `PUB_KEY_ID_...`。
- `wechatpayPublicKey`：微信支付公钥 PEM 内容。
- `apiV3Key`：32 个 ASCII 数字或大小写字母组成的 API v3 密钥。
- `notifyUrl`：唯一生产通知地址 `https://hm.kunagent.com/api/payments/webhooks/wechat`。
- `gatewayUrl`：唯一官方网关 Origin `https://api.mch.weixin.qq.com`。

原微信 `platformPublicKey` 字段不再作为微信渠道输入或持久化契约。由于项目尚未正式启用微信收款，不增加旧字段兼容读取；升级后旧微信配置必须显式重新填写，新契约未完整满足时渠道保持不可用。

### 支付宝渠道

支付宝仍使用现有 `platformPublicKey`，不新增微信公钥 ID，不改变签名、配置或接口契约。前后端类型应明确区分微信与支付宝配置，避免继续用一个共享字段承载两种不同语义。

## 后端职责

### 配置保存与 readiness

- 保存前验证微信公钥 ID 非空且以 `PUB_KEY_ID_` 开头，公钥可解析为 RSA 公钥，商户私钥可解析并可用于 RSA2 签名，API v3 密钥严格为 32 个 ASCII 字符。
- 启用微信渠道时，任何必填项不完整都拒绝保存；禁用状态允许分阶段录入，但不得出现在可用渠道列表。
- 公开配置只返回是否已配置密钥与公钥，不返回任何 PEM、API v3 密钥或公钥 ID 之外的敏感内容。公钥 ID 可在管理员配置响应中显示，用于核对当前生效事实。

### 出站请求

- 所有微信 API v3 请求继续使用商户私钥签名，`Authorization.serial_no` 使用商户 API 证书序列号。
- 所有请求额外发送 `Wechatpay-Serial: <wechatpayPublicKeyId>`，明确要求微信使用配置的公钥模式返回签名。
- 接收响应时必须读取 `Wechatpay-Serial`、`Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Signature` 和 `Request-ID`。
- `Wechatpay-Serial` 必须与当前配置的公钥 ID 完全一致；随后才允许使用配置公钥验证响应签名。缺头、错 ID、过期时间戳或坏签名均视为不可信响应，不得创建二维码、关闭交易或写入支付事实。

### 回调

- 回调 handler 必须采集 `Wechatpay-Serial`，service 首先验证其与当前公钥 ID 完全一致，再验证时间戳、随机串、签名和 API v3 密文。
- 公钥 ID 不一致、验签失败、密文解密失败、商户号/AppID/金额/币种不一致时，禁止履约并按现有 webhook 事实与 ACK 规则显式失败。
- 不根据未验签正文或错误消息切换公钥，不自动回退到平台证书。

### Request-ID 日志

- 每次微信 API 应答都写一条结构化日志，字段仅包含 `provider=wechat`、固定操作名、HTTP 状态码和微信返回的 `request_id`。
- `Request-ID` 缺失时仍记录明确的 `request_id_missing=true`，不能制造占位值。
- 日志禁止包含 Authorization、签名、私钥、公钥、API v3 密钥、二维码 `code_url`、checkout bearer、回调正文或商户订单号。
- Request-ID 日志不参与支付正确性判断；日志写入失败不得伪造支付成功。

## 前端职责

- 微信配置区新增“微信支付公钥 ID”，提示格式为 `PUB_KEY_ID_...`。
- 微信“平台公钥”字段硬切为“微信支付公钥”，说明其来源为商户平台 `账户中心 → API安全 → 微信支付公钥`。
- 支付宝继续显示“平台公钥”。两渠道使用可辨识的精确类型，不通过宽泛共享字段掩盖语义。
- 敏感字段保存后继续不回显；公钥 ID、商户号、AppID、证书序列号和 URL 可回显供管理员核对。
- 只有后端返回微信渠道 `ready=true` 时才显示“参数完整”；前端不自行推断支付已经接通。

## 数据与回滚

支付设置继续存放在现有系统设置 JSON 中，不新增数据库表或列。新版本读取单一新契约；旧微信字段不会自动映射。若回滚到旧版本，旧版本无法理解新微信公钥字段，因此回滚期间微信渠道必须保持禁用，恢复新版后重新核对配置。

## 失败策略

- 配置不完整或格式错误：保存请求失败并返回具体字段错误，不部分更新。
- 公钥 ID不一致或签名失败：应答/回调视为不可信，不生成二维码、不履约、不自动重试到另一套证书。
- 微信返回未知结果：沿用现有 `review_required` 和主动查单流程，不因 Request-ID 存在而判定成功。
- Request-ID 缺失：支付响应仍按签名和业务事实处理，但记录缺失事实，便于运营排查。

## 测试矩阵

### 后端单元与服务测试

- 启用微信时缺少公钥 ID、公钥、API v3 密钥或商户证书字段均拒绝。
- 公钥 ID 前缀错误、公钥或私钥 PEM 无效、API v3 密钥长度/字符不合法均拒绝。
- Native 下单、查单、关单请求都携带正确 `Wechatpay-Serial`。
- 正确公钥 ID与签名通过；缺失/伪造公钥 ID、错误公钥、正文变异、过期时间戳均失败。
- 回调缺失或伪造 `Wechatpay-Serial` 时不创建支付事实、不发放积分或会员权益。
- Request-ID 成功、非 2xx、缺失三类日志均可观察，且日志中不存在密钥、签名、二维码、bearer 或商户订单号。
- 支付宝现有配置、签名和测试保持通过。

### 前端测试

- 管理员 API 类型与表单使用微信专属公钥 ID/公钥字段，支付宝仍使用平台公钥。
- 微信启用时公钥 ID必填并显示精确来源说明；敏感内容不回显。
- 保存请求不再发送微信 `platformPublicKey` 旧字段。
- TypeScript、生产构建和现有支付配置测试全部通过。

### 完整回归

- 后端完整测试、race、vet、build。
- Web 完整测试、类型检查、生产构建与 bundle 预算。
- 支付集成测试继续运行 PostgreSQL 17/Redis 7 强制矩阵。
- 使用微信官方测试/真实小额商户环境完成 Native 下单、扫码支付、回调履约和后台交易/回调审计；未取得真实商户凭据前，该项必须保留为明确的生产验收门禁，不能用模拟签名宣称真实通道已接通。

## 非目标

- 不支持平台证书与微信支付公钥并存或自动切换。
- 不自动申请、下载、轮换或托管微信商户证书与公钥。
- 不记录或展示支付密钥，不增加明文诊断接口。
- 不在本次变更中发布版本、推送远端、修改生产配置或启用真实微信渠道。
