# 会员单弹窗扫码付款设计

## 目标

会员套餐的主购买路径必须呈现为一个完整、紧凑的扫码付款弹窗，而不是“确认购买弹窗 → 独立收银台页面”两段割裂流程。桌面端按产品确认的参考图尺寸重构：左侧展示冻结商品与订单事实，右侧展示真实支付渠道二维码、倒计时和会员服务协议入口；团队会员在同一弹窗内完成团队与席位确认。

本次是硬切换，不保留旧版宽大收银台或 `MembershipPurchaseModal` 作为并行购买路径。只复用参考图的信息结构、尺寸和视觉节奏，不复制 LibLib 品牌、协议正文、自动续费或其他未经本系统支持的承诺。

## 用户路径

### 全状态左侧一致性

- 订单创建前、订单创建中、checkout 恢复中、订单或 checkout 创建失败、二维码已生成及支付终态，左侧必须始终使用同一个订单事实展示组件和同一套 `766 / 425 / 341` 几何结构。
- 付款状态变化只允许替换右侧内容；禁止因为尚未获得 checkout token 而切回旧版 `880px` 购买确认布局、另一套标题层级或另一套订单明细表。
- 订单创建前的左侧事实来自用户当前选择的后台套餐与团队席位输入；订单创建成功后硬切为后端冻结订单摘要。两种来源必须映射到同一个显式展示模型，展示组件不得自行读取网络状态或推导未被上游证明的财务事实。
- 从可编辑套餐事实切换到冻结订单事实时，左侧 DOM 结构、视觉层级和栅格保持稳定，只更新订单号及服务端确认的价格、积分、席位等值。

### 个人会员

1. 用户点击套餐的“立即开通”。
2. 前端立即进入单一付款弹窗并创建幂等会员订单。
3. 创建或恢复该订单唯一的活动 checkout。
4. 已有活动交易时直接恢复真实二维码；只有一个可用渠道时直接创建该渠道交易；多个渠道时先要求用户选择真实渠道，再生成二维码。
5. 弹窗持续轮询服务端支付事实，成功、过期、关闭或待核对时原地切换状态，不跳转页面。

点击“立即开通”即是明确的创建订单意图，不再增加第二个普通确认弹窗。

### 团队会员

1. 用户点击团队套餐后打开同一个付款弹窗。
2. 左侧先展示团队选择或名称、席位数量与创建订单前的派生总额；右侧展示“确认配置并生成付款码”。
3. 用户确认后创建团队、幂等订单和唯一 checkout；订单创建成功后团队与席位控件锁定。
4. 右侧进入真实渠道选择或二维码状态。不得在二维码生成后修改团队、席位或金额。

### 历史订单与直接链接

- 会员订单中的“去支付”打开同一个付款弹窗并恢复该订单唯一的活动 checkout，不再导航到风格独立的全页收银台。
- `/pay/:token` 继续作为 bearer 直接访问、刷新恢复和外部链接入口，但必须复用同一付款体验组件，不维护第二套布局或状态机。
- 已过期或已消费 checkout 不得恢复为可支付二维码；按既有契约明确提示关闭旧订单后重新下单或等待渠道对账。

## 会员服务协议

- 法律文档领域新增独立的 `membershipAgreement`，与现有用户协议和隐私政策并列维护，不把会员付费条款混入普通用户协议。
- 管理后台“法律与协议”增加“会员服务协议”编辑项，继续复用现有富文本编辑、真实脏状态、离开保护、保存审计和公开预览能力。
- 新增公开路由 `/legal/membership-agreement`，页面标题为“HMaigc会员服务协议”，内容只来自后台已保存事实。
- 二维码下方固定显示“开通即代表同意《HMaigc会员服务协议》”，协议名称为可键盘访问的真实链接，并在新标签页打开。
- 协议尚未发布时，公开页面明确显示“会员服务协议尚未发布”；按产品确认，该状态不阻止创建会员订单、创建 checkout、生成二维码或完成支付。
- 本轮只增加协议展示和访问入口，不增加勾选框、电子签署、版本签收记录或支付前强制同意门禁。

## 视觉结构

### 桌面

- 弹窗唯一外壳宽度为 `766px`，目标高度约 `472px`；内容增加时允许自然增高，不裁切真实错误、长套餐名或团队事实。
- 左侧订单区为 `425px`，右侧支付区为 `341px`。两区只由背景明度和一条直线分隔，不使用嵌套外框。
- 标题格式为“开通创作会员「套餐名 周期」 积分数量”或团队对应事实，关闭按钮位于右上角。
- 左侧依次为商品信息、订单明细、原价、优惠和应付金额。原价不高于实付时隐藏优惠行，禁止前端伪造折扣。
- 商品信息块只保留真实当前选择的青色边界；订单明细使用连续表面和弱分隔，不堆叠圆角卡片。
- 右侧居中展示支付提示、二维码、交易剩余时间和会员服务协议入口。交易创建后不再重复显示支付方式卡片和锁定说明。
- 创建中、创建失败和 checkout 恢复失败只在右侧展示加载、错误与重试操作；左侧仍完整呈现标题、商品信息卡和订单明细，不得降级为旧购买摘要。
- 二维码图形目标尺寸为 `112px`，包含不可变白色静区后的整体目标尺寸为 `128px`。二维码必须保持黑色前景、白色背景、至少四模块静区和可扫码性，不随明暗主题反转。
- 多渠道选择只在尚未创建交易时出现；交易创建后渠道锁定，禁止制造第二笔可支付交易。

### 平板与移动端

- `768px` 视口下弹窗最大宽度为视口减 `48px`，保持左右双栏；左右栏按 `425:341` 比例收缩，但二维码整体仍保持 `128px`。
- `390px` 视口使用单列，弹窗宽度为视口减 `32px`，订单事实位于上方，二维码和协议入口位于下方。
- 弹窗内容自然纵向滚动，不能通过隐藏横向溢出掩盖布局错误。
- 所有主要按钮、渠道选择、关闭按钮和团队输入热区不小于 `44px`。

### 设计系统

- 只消费 `design-tokens.css` 的语义颜色、间距、圆角、阴影和焦点变量。
- 二维码前景与背景继续使用已审核的不可变黑白 QR token，不在业务组件散落新的颜色常量。
- 外壳是唯一拥有可见边界和圆角的付款容器；内部表面为直角，只有真实选择控件可保留语义选中边界。
- 字体、金额层级、分隔和留白按参考图收紧，但正文仍满足 WCAG 2.1 AA 对比度，不通过低对比度模拟参考站。

## 组件与领域边界

### `MembershipPaymentDialog`

负责弹窗开关、个人或团队购买输入、订单创建、checkout 恢复及当前 token 生命周期。它不自行计算财务事实；创建订单前把当前套餐与席位映射为待确认展示事实，订单创建后把后端冻结摘要映射为已确认展示事实，两者交给同一左侧组件渲染。

### `PaymentCheckoutExperience`

承载 checkout GET/POST、单飞、防乱序、轮询、渠道锁定和终态收敛。弹窗与 `/pay/:token` 入口复用同一个组件，不复制网络状态机。

### 展示组件

- `MembershipOrderFacts`：单一左侧展示组件，只接收已规范化的订单事实展示模型；同时服务订单创建前、创建中、创建失败、二维码和终态，不读取请求状态。
- 待确认展示模型只能由当前后台套餐字段、计费周期和有效席位输入派生；冻结展示模型只来自服务端 checkout 摘要。两者不得共享隐式默认值或伪造折扣。
- `PaymentQrPanel`：只展示渠道选择、二维码、倒计时、协议入口、支付错误和终态。
- 团队购买输入属于订单创建前区域；订单创建成功后由冻结摘要替换，不与结算摘要并行显示。
- 协议入口使用共享法律文档路由常量，不在支付组件中拼接外部品牌 URL 或协议正文。

### 法律文档领域

- 后端法律设置 DTO、验证、持久化和公开读取统一增加 `membershipAgreement`，不创建支付领域的第二份协议存储。
- 管理后台法律编辑器和公开法律页继续复用同一数据源；支付组件只依赖稳定公开路由，不读取或缓存协议正文。
- 协议保存继续沿用管理员权限、结构化审计和富文本安全清洗契约。

## 数据与状态流

1. 套餐按钮提供 `planId/teamId/seats` 购买输入。
2. 订单请求继续使用与规范化购买指纹绑定的 `Idempotency-Key`；重复点击或网络重试只能得到同一订单。
3. checkout 创建继续由后端保证同一订单只有一个 session，并只恢复仍在有效期内的 active URL。
4. 交易创建继续使用当前单一 payable 约束；前端同步单飞，后端数据库约束是最终一致性边界。
5. 二维码只来源于 `activeTransaction.codeUrl` 或成功的交易创建响应，禁止测试占位、静态图片或前端生成假支付地址。
6. 支付成功、迟到到账、过期、关闭和 `review_required` 均以服务端事实为准，前端不得伪成功。
7. 会员服务协议通过现有站点法律设置接口独立发布；协议是否为空不参与支付订单、checkout 或交易状态机。

## 失败与关闭行为

- 订单创建失败：弹窗保留购买输入并原地显示真实错误，可重试同一幂等请求。
- checkout 创建失败：若订单已经创建，显示订单号和“订单已创建但付款入口失败”，允许恢复该订单，不重新创建订单。
- 无可用渠道：右侧明确显示“当前没有可用支付渠道”，不得渲染空白二维码区。
- 渠道创建交易失败：保留左侧冻结摘要和已选渠道，右侧原地重试，不清空事实。
- 轮询瞬时失败：保留二维码和上次成功摘要，显示同步失败提示。
- 写请求进行中禁止关闭弹窗；二维码生成后允许关闭，但明确说明订单仍为待支付，可从订单记录继续。
- 弹窗关闭只停止前端轮询，不取消订单、不关闭商户单。
- 协议读取失败或尚未发布：公开协议页显示真实失败或未发布状态，不影响已打开收银台和付款状态。

## 测试与验收

### 自动化

- 纯状态测试覆盖个人直接创建、团队配置锁定、订单幂等、多个渠道选择、单渠道直接生成、已有二维码恢复、写入单飞和 token 切换。
- 组件测试必须证明购买主路径不再渲染旧“确认购买 / 创建订单并支付”弹窗，也不调用 `window.location.assign` 跳转付款页。
- 组件测试覆盖无渠道、订单已创建但 checkout 失败、交易失败、轮询失败、成功、过期、关闭和待核对。
- 法律文档测试覆盖会员服务协议的管理员读取与保存、公开读取、富文本清洗、审计、未发布空状态和现有用户协议/隐私政策不回归。
- 协议入口测试覆盖链接文案、公开路由、新标签安全属性、已发布和未发布均不阻断支付。
- 组件测试覆盖创建中、订单创建失败、checkout 恢复失败和活动二维码四种状态，证明左侧复用同一个订单事实组件、标题/商品卡/明细 DOM 结构一致，且弹窗宽度始终为 `766px`。
- 后端支付并发、checkout 与交易唯一性继续运行完整 PostgreSQL 17/Redis 7 门禁。

### 真实浏览器

- 在生产 Docker/Nginx 构建中验证 `1440×900`、`768×1024`、`390×844` 的明暗主题。
- 个人、团队、积分、单渠道、多渠道、活动二维码和所有终态均检查无横向溢出、真实焦点顺序、44px 移动触控与 QR 黑白静区。
- 浏览器必须测量桌面 `766px` 外壳、`425/341px` 双栏和 `128px` 二维码整体尺寸，并拒绝用动画中间帧或 overflow 隐藏制造假通过。
- 浏览器必须验证从套餐按钮到二维码始终停留在同一弹窗；`/pay/:token` 直接入口使用同一内容结构。
- 浏览器必须验证协议链接可访问，协议未发布时公开页显示真实空状态且付款二维码仍保留。

## 非目标

- 不新增支付渠道、退款接口、自动续费、分期、协议勾选、电子签署或协议版本签收记录。
- 不伪造本地演示二维码；本地未配置商户渠道时只能展示明确配置错误。
- 不改变会员套餐、积分发放、并发权益、支付验签或履约数据库规则。
- 不复制 LibLib 品牌、协议内容或任何不属于 HMaigc 的法律承诺。
